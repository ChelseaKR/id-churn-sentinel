# 4. Count visits to the two web pages with Google Analytics 4

## Status

Accepted, 2026-09-18. Decided by the project's owner, Chelsea Kelly-Reif.

This changes the rule that gate 6 (`make no-unreviewed-in-feed`) enforced about third-party
requests. It does not change any other safety property. The numbering continues after
`docs/decisions/0001` to `0003`, so no number means two things.

## Context

Until this decision the published site loaded nothing from any third party. The reason is
written down in three places, and it still stands:

- `docs/RESPONSIBLE-TECH-AUDITS.md` §C: *"Anyone who subscribes to a feed of trans
  identity-document law changes is, with high probability, a trans person or someone working
  directly with trans people. In the current US environment, that list is a targeting
  artifact. It could be subpoenaed, breached, sold, or handed over."* The mitigation it names
  is *"not to secure the list. It is to never create it."*
- `docs/06-SECURITY-PRIVACY-THREAT-MODEL.md` lists subscriber surveillance as a threat, and
  names referral analytics and reader location as data not to collect.
- `tests/test_site.py` held the published pages to zero third-party requests in the
  merge-blocking gate, and the Makefile says that when a safety gate goes red, the answer is
  to stop, not to weaken the test.

An earlier attempt to add Google Analytics 4 stopped at that gate for that reason.

On 2026-09-18 the owner decided to add GA4 here as on her other 25 public sites ("fix all
of … id-churn-sentinel"). The property is 554857497 and the web stream's measurement ID is
`G-98S46JC943`. The property was provisioned with 14-month data retention and Google signals
off. In the stream's enhanced measurement, page views from browser-history events, site
search and form interactions are off.

## Decision

Google Analytics 4 counts visits to the two HTML pages, `index.html` and `privacy.html`,
within these limits. `src/id_churn_sentinel/core/analytics.py` implements them in one inline
loader.

1. **The feeds and data files never load it.** `feed.xml`, `changes.json`, `sources.json`,
   `status.json` and every per-jurisdiction file are what a clinic subscribes to. They carry
   no script, and fetching one sends nothing to Google.
2. **Production only.** The loader does nothing unless the page is served from
   `chelseakr.github.io` under `/id-churn-sentinel/`. `make serve`, a local file, the test
   suite and CI never contact Google.
3. **Refusable.** It loads nothing, and sets no cookie, when `navigator.globalPrivacyControl
   === true`, when Do Not Track is on (`navigator.doNotTrack`, `window.doNotTrack` or
   `navigator.msDoNotTrack` is "1" or "yes"), or after the footer's "Opt out of analytics".
   That choice is stored in localStorage under `id-churn-sentinel:analytics-opt-out`. The key
   names this project because every `chelseakr.github.io` site shares one origin.
4. **No advertising.** Consent Mode v2 defaults deny `ad_storage`, `ad_user_data` and
   `ad_personalization` everywhere. `analytics_storage` is denied in the EEA, the UK and
   Switzerland through `region`, which means cookieless pings there, and granted elsewhere.
   There is no banner, so nothing grants the denied ones. `allow_google_signals` and
   `allow_ad_personalization_signals` are both false.
5. **The address, and nothing a reader chose.** This limit is stricter than on the owner's
   other sites, because of who reads this one. `page_location` is the origin plus the path:
   the query string and the fragment are never read, so they are never sent. `page_referrer`
   is the referring site's origin only. The pages have no form field. The loader sets no
   `user_id`, no user property and no custom event, so nothing a reader types and nothing
   that identifies them is ever an event parameter.
6. **A privacy page.** `privacy.html` is generated by `sentinel publish` and linked from both
   footers. It says what Google receives and what it never receives, names the cookies, the
   retention and the three ways to turn analytics off, and states the GitHub hosting limit.

### How gate 6 changed

The gate was changed, not disabled. It now enforces this decision:

- **Exactly one script is allowed.** It is the loader `analytics.head_snippet` renders,
  matched by its whole text and by a SHA-256 digest pinned in `tests/test_site.py`, outside
  the module that renders it. It may appear once, only inside the `<head>` of an HTML page.
  Only that exact text is removed before the old checks run, so a loader that differs by one
  character (a guard dropped, another ID, Google signals on, the full address sent) is not
  removed and fails as a stray `<script>`.
- **Everything the old rule forbade is still forbidden**, on the front page and in every
  published artifact: any other script, stylesheet, font, image, iframe, form, pixel,
  beacon, tracking parameter or third-party host. A feed or data file gets nothing removed,
  so the loader itself fails there.
- **The permission is checked on its own.** Only this measurement ID is allowed, the only
  external address is Google's tag script for this ID, every guard is present once, and the
  loader never touches `location.search`, `location.hash`, `location.href`, cookies, input
  values, `sendBeacon`, `fetch`, custom events or `user_id`.
- **Negative controls prove both halves.** The intact published site passes. A web font, a
  second script, an inline beacon, a pixel, an iframe, the loader twice, the loader in the
  body, another measurement ID, each guard removed, Google signals on, the full address, a
  custom event, and the loader in a feed or JSON file each fail. Each control asserts that
  its sabotage changed the page first.
- **The loader is executed.** `tests/test_analytics.py` runs it in Node against a stubbed
  browser. It proves each guard stops the load, and that a visit whose address and referrer
  carry a name, an email address, a date of birth and a search term sends none of them. It
  also removes each guard and each scrub in turn and checks that the harness sees the load
  or the leak.

Changing the loader changes the pinned digest. A change to when it loads or to what Google
receives needs a new decision record, not just a new digest.

## Consequences

**The risk this accepts, stated plainly.** Visits to the two web pages now reach Google LLC,
a US company outside this project's control. Each visit carries a pseudonymous client
identifier in the `_ga` cookie, the reader's IP address (Google says GA4 uses it to derive
approximate location and does not store it), the page path, the referring origin, and
browser and device details. That is a record, held by a third party, of browsers that read
about trans identity-document law. It is not a subscriber list and it holds no name or email
address, but it is the kind of data §C and the threat model were written to avoid, and it
could be subpoenaed or requested from Google. The project can no longer say that it has no
data about who reads its pages. It can still say that about the feeds.

**Mitigations, and what each one buys.**

- The feeds, the part a clinic integrates, are untouched. Someone who does not want to be
  counted can read the feeds and never load a page.
- GPC, DNT and the footer opt-out each stop the loader before any request is made.
- Readers in the EEA, the UK and Switzerland get no analytics cookies.
- Ad features and Google signals are off, so the data is not joined to Google advertising
  profiles through this property.
- The address carries no query string or fragment, and the referrer carries no path, so a
  search someone typed elsewhere, or anything a link adds to the address, does not reach
  Google.
- Event-level data is kept for 14 months, not indefinitely. Aggregate counts in GA4's
  standard reports are not covered by that setting.

**Residual risks, named rather than implied.**

- The pages still tell Google which pages were visited. The sources table links to official
  pages for each state, and GA4's enhanced measurement records outbound clicks and file
  downloads by default. That means Google can learn which state's page a reader followed.
  The owner can turn off *Outbound clicks* and *File downloads* in the web stream's
  enhanced measurement settings. The privacy page describes the current default.
- `chelseakr.github.io` is shared by the owner's other project sites, and the `_ga` cookie
  is set for the whole origin. The same client identifier therefore reaches the analytics of
  each sibling site that runs GA. The privacy page says so. A cookie prefix or path for this
  site alone would separate them, but it was not adopted, to keep the one loader pattern the
  portfolio uses.
- GitHub's access logs, the limit §C already names, are unchanged.

**What changed elsewhere.** `docs/RESPONSIBLE-TECH-AUDITS.md` §C,
`docs/06-SECURITY-PRIVACY-THREAT-MODEL.md`, `docs/CONSUMERS.md`, `docs/ROADMAP.md`, the
README, `CLAUDE.md` guardrail 5, the V1 planning documents and the page copy now describe the
pages as counted and the feeds as untracked, so no document still claims the site has no
analytics. The page description, and the social card drawn from it, now end with "No
account; the feeds carry no tracking."

**Reversal.** Setting `GA4_MEASUREMENT_ID = ""` in `core/analytics.py` and running
`make publish` removes the loader, the footer control and every reference to Google from both
pages, and makes the footer and privacy page say that the site runs no analytics. The gate's
pinned permission in `tests/test_site.py`, and the tests in `tests/test_analytics.py` that
expect the loader on the committed pages, then have to be updated to permit no script at
all, which is the rule this decision replaced. Reversing this decision should be recorded as
a new ADR that supersedes this one.
